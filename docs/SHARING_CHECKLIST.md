# Sharing and Submission Checklist

Complete this checklist before placing the repository on GitHub Pages or submitting the website as a TDG deliverable.

## Project information

- [ ] Confirm the project title, project number, PI, Core Members, Contributors and department.
- [ ] Confirm that the project outline matches the final report.
- [ ] Confirm the selected TDG sharing level: public, HKU staff and students, or HKU staff only.
- [ ] If the selected level is not public, use an access-controlled HKU environment instead of public GitHub Pages.

## Student work

- [ ] Obtain written permission to disseminate each selected student figure.
- [ ] Confirm whether student names should appear or remain omitted from the shared page.
- [ ] Remove student numbers, email addresses, assessment comments and other personal identifiers.
- [ ] Confirm that sharing assessed work is consistent with relevant course and university procedures.
- [ ] Keep full-resolution student material outside the public repository.

## Images, maps and data

- [ ] Verify the licence or permission for each ground-truth street-view image.
- [ ] Verify the licence and permitted dissemination of satellite, mobile-activity, map and contextual datasets.
- [ ] Retain required data-source and map attributions in the final shared materials.
- [ ] Confirm that synthetic images may be shared together with their source-derived comparisons.
- [ ] Confirm that Phase 2 student figures are limited to the reduced-resolution watermarked previews.

## Human-rating demonstration

- [ ] Keep the statement that responses remain in the visitor's browser.
- [ ] Do not claim that the public demonstration aggregates or analyses visitor responses.
- [ ] Do not present the supplied rating protocol as completed human-subject results when no completed ratings are recorded.
- [ ] If central data collection is added later, complete an ethics, consent, privacy and data-management review before deployment.

## Claims and academic language

- [ ] Retain the exact three phase titles from the project proposal.
- [ ] Present Phase 1B as a teaching extension rather than a fourth formal project phase.
- [ ] Retain the distinction between measured brightness, perceived environment, observed activity, social interaction and safety.
- [ ] Describe the supplied Phase 2 evidence as comparative and associational unless predictive-model results are added.
- [ ] Describe the MVI study as parametric or AI-ready design search unless a trained generative-model workflow is documented.
- [ ] Retain the statement that the Phase 2–Phase 3 connection is an integrated teaching framework rather than a completed causal experiment.

## Web quality

- [ ] Test the site at desktop, tablet and mobile widths.
- [ ] Confirm that every image loads from a relative path on GitHub Pages.
- [ ] Confirm keyboard operation of image controls and analysis/design tabs.
- [ ] Confirm that all images have meaningful alternative text.
- [ ] Confirm sufficient contrast and visible keyboard focus.
- [ ] Test browser-local rating storage, CSV download and data clearing.
- [ ] Run the automated website and teaching-code tests and resolve every failure.
- [ ] Retain `teaching_code/UPSTREAM_NIGHTDIFF_LICENSE.txt` and the modification notice when the adapted teaching script is shared.

## Submission package

- [ ] Include the GitHub Pages URL in the TDG deliverables email.
- [ ] Include a ZIP archive of this repository as a recoverable electronic copy.
- [ ] Include the project outcome presentation as a separate deliverable when available.
- [ ] Complete the standard final-report form separately.
- [ ] Attach current Financial Information Dashboard screenshots for both the Central Fund account and the Faculty Matching Fund account.
